# adr-new — 새 ADR 생성

lab-trading의 결정 추적 인프라. 사용자가 "되돌리기 어려운 결정"을 내렸거나 내릴 예정일 때 호출되어 ADR 1개를 생성하거나, 기존 ADR의 상태를 갱신한다.

## 언제 트리거되는가

다음을 언급하면 본 스킬을 사용한다:
- "ADR 작성/추가/만들어/등록/업데이트"
- "결정 기록", "결정 문서"
- "architecture decision record", "디시전 레코드"
- "이거 ADR로 남겨"

다음은 트리거하지 않는다 (페이지 추가, 어댑터 옵션 변경, 카피 수정 같은 일상 변경 — `docs/adr/README.md`의 작성 기준 참조). 사용자가 의도를 명확히 하지 않은 경우 "이건 ADR로 남길 만한 결정인가? 아니면 일상 변경인가?"를 짧게 확인한다.

## 1차 출시 전 특수 상황

현재(2026-05-12) lab-trading의 모든 ADR(0001-0020)은 `Proposed` 상태로 시작했다. 사용자 검토 후 일괄 `Accepted` 전환이 예정되어 있다. 이 동안:

- 새 ADR도 `Proposed`로 시작.
- 사용자 검토 완료 알림이 들어오면, **이미 작성된 ADR 0001-0020을 일괄 `Accepted` 전환** 후 README 인덱스도 동기화.

## 워크플로우 — 신규 생성

### 1. 다음 번호 결정

`docs/adr/` 안의 `ADR-NNNN-*.md` 파일을 스캔하고, 가장 큰 NNNN + 1을 다음 번호로 사용한다.
- 예: `ADR-0020`까지 있으면 다음은 `ADR-0021`.
- 4자리 0-padding 유지.
- `template.md`, `README.md`는 제외.

### 2. 사용자에게 핵심 정보 수집

대화형으로 받는다(가능한 한 한 번에 묶어 묻고, 사용자 메시지에 이미 충분한 컨텍스트가 있으면 추가 질문 없이 바로 작성):

- **제목** (한국어 짧게, 예: "Web Worker 백테스트 이전")
- **컨텍스트** — 왜 결정이 필요한가? 어떤 제약·요구가 있는가?
- **검토한 옵션** — 최소 2개 (장단점 포함)
- **결정** — 어떤 옵션을 골랐고 왜?
- **결과** — 긍정·부정·후속 작업

### 3. 슬러그 생성

제목을 영어 kebab-case 슬러그로 변환한다.
- 한국어 제목이면 의미를 영어로 옮겨서 슬러그 작성. 예: "백테스트 엔진 이전" → `backtest-engine-migration`.
- 슬러그는 짧게(1~4 단어). 파일명: `ADR-NNNN-<slug>.md`.
- 슬러그 규칙(영어 kebab-case)은 CLAUDE.md의 컨벤션 H와 동일.

### 4. 파일 생성

`docs/adr/template.md`를 베이스로 채워 `docs/adr/ADR-NNNN-<slug>.md`에 쓴다.
- 상태: 기본 `Proposed`. 사용자가 명확히 "확정/Accepted"라고 했으면 `Accepted`.
- 날짜: 오늘(YYYY-MM-DD).
- 결정자: 사용자에게 묻거나 git config user.name 사용.

### 5. 인덱스 갱신

`docs/adr/README.md`의 인덱스 테이블 마지막 행에 한 줄 추가한다. 형식:

```
| [NNNN](ADR-NNNN-<slug>.md) | <제목> | <상태> | <사용자 결정 필요?> |
```

### 6. 보고

생성한 파일 경로와 상태를 사용자에게 1~2줄로 보고한다.

## 워크플로우 — 상태 갱신

기존 ADR의 상태를 바꾸는 요청("ADR-0001을 Accepted로", "ADR-0003 Deprecated", "ADR 0001-0020 일괄 Accepted") 처리:

1. 해당 파일의 frontmatter 영역 `상태:` 라인을 갱신한다.
2. `Superseded by ADR-XXXX`로 변경하는 경우, 새 ADR을 신규 생성 워크플로우로 만들고 이전 ADR의 상태에 새 번호를 박는다.
3. `docs/adr/README.md` 인덱스의 해당 행 상태 컬럼도 동기화한다.
4. 일괄 변경 시(사용자 검토 통과 후 모든 Proposed → Accepted): 변경된 ADR 번호 범위를 보고.

## 작성 원칙

- 본문은 **한국어** (CLAUDE.md 컨벤션 G와 정합).
- 옵션 비교는 **결정적 트레이드오프**에 집중. 자명한 장단점 나열 회피.
- "결정" 섹션은 짧게: 한 옵션을 고른 결정적 이유 1~2문단.
- "결과 — 부정적"에 반드시 **완화 방안**을 함께 적는다.
- "따라오는 작업"이 새 ADR을 낳을 가능성이 있으면 명시("...는 별도 ADR로").
- 길이는 80~200줄 목표. 데이터 소스·어댑터 결정 같은 정보량 많은 ADR은 200줄+ 허용.

## 트리거 검증 가이드

본 스킬이 트리거되어야 하는 케이스(예시):
- "Web Worker로 백테스트 이전하는 거 ADR로 남기자"
- "Polygon 어댑터 추가 결정 박아"
- "ADR-0007 Accepted로 바꿔줘"
- "한국 주식 어댑터에 키움 추가하기로 했으니 ADR"

본 스킬이 트리거되면 안 되는 케이스(예시):
- "백테스트 결과 카드 색 살짝 바꿔" (디자인 미세 조정)
- "버튼 hover 효과 추가" (스타일링)
- "타이포 고쳐" (단순 수정)

경계 케이스("어댑터 polling 간격 조정"처럼)에는 사용자에게 "ADR로 남길 변경 규모인가요?"를 1줄로 확인한다.
